# SpiritLM

Next.js App Router, Clerk, Prisma 7 и MariaDB. Кабинет использует реальные ключи, баланс и статистику из базы данных.

## Локальный запуск

```bash
npm install
npm run db:generate
npm run dev
```

После изменения Prisma-схемы примените миграции (`npm run db:migrate`),
выполните `npm run db:generate` и полностью перезапустите `npm run dev`.
Горячая перезагрузка Next.js может удерживать старый Prisma-клиент в памяти:
новые поля тогда вызывают ошибку валидации даже после успешной миграции.

Настройки берутся из `.env.local`, затем `.env`. Образец — `.env.example`.

- `DATABASE_URL` — подключение отдельного пользователя к базе `spiritlm`.
- `CHEAPVIBE_API_KEY` — серверный ключ поставщика, без префикса `NEXT_PUBLIC_`.
- Clerk: `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` и `CLERK_SECRET_KEY`.

Секреты не добавляются в Git. Для текущей среды база `spiritlm` уже создана, начальная миграция применена, локальное подключение сохранено.

## База данных

Для нового сервера передайте административную строку подключения переменной `DATABASE_ADMIN_URL` только на время команды:

```bash
npm run db:init
npm run db:migrate
```

`db:init` создаёт базу `spiritlm` и отдельного пользователя с правами только на неё. Строка подключения сохраняется в `.env.local`; другая база на сервере не используется. Повторная инициализация при существующем `DATABASE_URL` или непустой базе отклоняется. Публичный сервер должен использовать проверяемое TLS-подключение: для инициализации задайте `DATABASE_REQUIRE_TLS=true`, для приложения добавьте `sslaccept=strict` в URL, если сервер поддерживает TLS и имеет доверенный сертификат.

Миграции находятся в `prisma/migrations`. Команда `db:migrate` применяет только сохранённые миграции к базе из `DATABASE_URL`; запускать отдельно перед развёртыванием. `migrate reset` и `db push` для рабочей базы не использовать.

На NixOS для CLI можно задать локальную переменную `PRISMA_SCHEMA_ENGINE_BINARY` с путём к установленному `schema-engine`, соответствующему Prisma 7.8. Приложение использует JavaScript-драйвер MariaDB и не требует нативного движка запросов. Эту локальную переменную не переносить на Netlify или Vercel.

## Ручное начисление баланса

Clerk User ID можно взять в панели Clerk. Команда может создать запись пользователя до его первого посещения кабинета:

```bash
npm run balance:credit -- user_CLERK_ID 1000 payment-20261020-001 "Пополнение вручную"
```

Сумма в рублях, до восьми знаков после точки. Идентификатор операции должен быть уникален. Повтор той же операции не начисляет деньги повторно; изменение пользователя, суммы или комментария при том же идентификаторе отклоняется. Начисление и обновление баланса выполняются одной транзакцией; история видна пользователю в кабинете.

## Пополнение через CryptoBot

В `.env.local` задайте `CRYPTO_BOT_MODE=test` и `CRYPTO_BOT_TOKEN_TEST`
от приложения в `@CryptoTestnetBot`. Для рабочего окружения используются
`CRYPTO_BOT_MODE=live` и `CRYPTO_BOT_TOKEN` от `@CryptoBot`. Без явно выбранного
режима пополнение отключено; подстановка рабочего токена вместо тестового
не выполняется.

Перед запуском примените миграции и перезапустите dev-сервер:

```bash
npm run db:migrate
npm run payments:check
npm run dev
```

`payments:check` выполняет только `getMe`, проверяет авторизацию и идентификатор
приложения. Счёт не создаёт и токен не выводит.

В кабинете откройте пополнение, задайте сумму и нажмите «Создать счёт», затем
«Оплатить в Telegram». Счёт выставляется в RUB, оплата принимается в USDT и TON
(после переименования актива отображается как Gram),
срок действия — 30 минут, диапазон — 100–100 000 ₽. Зачисляется полный номинал;
комиссия провайдера покрывается сервисом. Это начальные настройки интеграции,
их нужно подтвердить перед рабочим запуском.

На localhost HTTPS-туннель не обязателен: открытая модалка опрашивает сервер
раз в 10 секунд, сервер проверяет счёт через Crypto Pay. Тестовая оплата
увеличивает только `User.testBalance`, показанный в модалке. Рабочий баланс
и история реальных начислений остаются отдельными. Используйте тестовые средства
`@CryptoTestnetBot`; рабочие USDT для этого сценария не нужны.

Для уведомлений настройте в приложении Crypto Pay публичный HTTPS-адрес
`/api/payments/cryptobot/webhook`. При локальной проверке webhook понадобится
HTTPS-туннель. Подпись проверяется по исходному телу запроса; повторная доставка
не даёт повторного начисления. Пользователь не обязан связывать Telegram с Clerk:
платёж принадлежит аккаунту, который создал его на сайте.

Для восстановления оплаты при закрытом браузере или пропущенном webhook
настройте запуск `npm run payments:reconcile` раз в минуту в том же окружении.
Один запуск обрабатывает до 50 давно не проверявшихся платежей; при большом
объёме увеличьте частоту запуска. Неоплаченные истёкшие счета сверяются ещё
семь дней. Смена приложения Crypto Pay требует завершить сверку старых счетов
со старыми настройками перед переключением.

Если ответ создания счёта потерян, запись остаётся в статусе `CREATING`.
Сервис ищет счёт по внутреннему ID в `payload`, повторно `createInvoice` для
той же записи не вызывает. При подтверждённом отказе провайдера ставится `FAILED`.
Если неопределённый результат не восстанавливается, поддержке нужно сверить
счета приложения и внутренний ID платежа; автоматически помечать такую запись
оплаченной или повторно создавать счёт нельзя. За один проход поиска
проверяется до 2 000 счетов; при превышении требуется ручная сверка.
Если полная успешная сверка не находит счёт и с создания прошло 30 минут,
запись закрывается как `FAILED`, после чего можно оформить новое пополнение.

Банковские карты подключены отдельно через тестовый магазин ЮKassa.
Подробный [план подключения](docs/cryptobot-top-up-plan.md) сохранён отдельно.

## API и текущий статус

Подробная пользовательская документация находится в кабинете на `/dashboard/docs`: эндпоинты, коды ошибок, curl, Python/JavaScript SDK и настройка агентов.

- `GET /v1/models` — доступные модели SpiritLM; нужен Bearer-ключ SpiritLM.
- `POST /v1/chat/completions` — контракт Chat Completions, включая SSE. Для запроса резервируется баланс, затем списывается цена по usage.
- `/api/dashboard/keys` — управление собственными ключами через сессию Clerk.
- `/api/dashboard/summary` — баланс, история начислений, последние запросы, почасовой расход за 48 часов и разбивка по моделям.

Секрет SpiritLM выдаётся один раз при создании; в базе хранится SHA-256-хеш криптографически случайного ключа и префикс. Отозванные ключи перестают работать. Сессия Clerk не заменяет ключ `/v1`.

Публичные ID сохраняют существующий вид, например `deepseek/deepseek-v4-flash`. Адаптер сопоставляет их с подтверждёнными ID CheapVibe, например `deepseek-v4-flash`. Список поставщика кешируется на 30 секунд внутри процесса. Каталог на сайте содержит утверждённые тарифы; фактическую доступность моделей показывает `/v1/models`.

Общего ограничения вывода в 4096 токенов нет: `max_tokens` или `max_completion_tokens` передаётся поставщику без уменьшения. Верхняя граница берётся из объявленного лимита конкретной модели; `/v1/models` возвращает её как `max_output_tokens`, если она известна. При отсутствии параметра прокси не подставляет собственный лимит.

Цены в каталоге — утверждённые тарифы в рублях за 1 MTok. Перед запросом система резервирует верхнюю оценку стоимости по размеру входа и лимиту вывода. После ответа списывается фактическая цена по usage, а остаток резерва возвращается. Для запроса нужен положительный баланс. Диагностические запросы записывают расчётную стоимость, но баланс не затрагивают.

Статистика запросов включает входящие, исходящие, общие, кэшированные и reasoning токены, когда поставщик возвращает эти поля. Кэш и reasoning повторно не прибавляются к total_tokens. Поле поставщика `credit` не интерпретируется как рублёвая себестоимость. Переписки и ответы в базе не сохраняются.

При обрыве или отсутствии итогового usage расход остаётся неизвестным, а не нулевым; в этом случае удерживается резерв. При подтверждённой upstream-ошибке резерв возвращается. Старые RUNNING-запросы восстанавливаются как прерванные при следующем запросе пользователя, а их резерв учитывается как списание с неизвестным usage. Автоматических повторов генераций нет.

Пока подключён только Chat Completions; Responses, Anthropic Messages, Codex и Claude Code не подключены.

## Проверки

```bash
npm run typecheck
npm run lint
npm run test:unit
npm run test:backend
```

Операции Prisma организованы в `src/actions/<operation>/` с `index.ts`, `schema.ts`, `types.ts` и общей обёрткой `createSafeAction`. Публичные действия проверяют сессию; внутренние операции прокси и начисления не являются публичными Server Actions. Конкурентные операции используют Serializable-транзакции с максимум тремя попытками при P2034. Ручных SQL-запросов в приложении нет. HTTP-запросы выполняются через `ky` без автоматических повторов.

Автономные тесты находятся в `tests/*.test.ts`, интеграционные разделены по областям в `tests/integration/`, общие фикстуры — в `tests/helpers/`. Интеграционные проверки используют базу из `DATABASE_URL`, временных пользователей и имитацию CheapVibe и Crypto Pay. Запускайте их с отдельной мигрированной тестовой базой. Тестовые записи удаляются, реальные платежи и генерации не выполняются.

Для явной проверки владельцем с реальной генерацией:

```bash
npm run proxy:smoke -- user_CLERK_ID
npm run proxy:smoke -- user_CLERK_ID --stream
```

Каждая команда делает ровно один запрос `deepseek-v4-flash` с лимитом восемь выходных токенов, без повторов. Запрос отмечается диагностическим, попадает в статистику указанного пользователя и не списывает его баланс. При таймауте фактический расход у поставщика может остаться неизвестным.

`npm run build` в этой рабочей сессии не запускается согласно AGENTS.md.

## Netlify

Проект можно подключить к Netlify как Next.js-приложение: App Router, middleware,
SSR и API routes обрабатываются Next.js adapter, который Netlify подключает
автоматически. Настройки сборки зафиксированы в `netlify.toml`.

1. Запушьте проект в GitHub/GitLab и в Netlify создайте сайт через **Add new
   project → Import an existing project**. Укажите корень репозитория как Base
   directory. Команда сборки — `npm run build`, папка публикации — `.next`.
2. В **Project configuration → Environment variables** добавьте переменные ниже
   для Production и Deploy Previews, где это необходимо. Не копируйте `.env.local`
   в репозиторий, не задавайте `DATABASE_ADMIN_URL` и удалите
   `PRISMA_SCHEMA_ENGINE_BINARY` из переменных Netlify, если она там есть. Это
   локальная настройка NixOS; её путь `/run/current-system/sw/bin/schema-engine`
   недоступен в окружении Netlify и ломает `prisma generate` при установке.
3. Разрешите сетевой доступ к MariaDB с серверов Netlify и используйте отдельного
   пользователя приложения. Хост базы должен быть доступен из интернета и
   поддерживать TLS; добавьте `sslaccept=strict` в `DATABASE_URL`.
4. Примените миграции к production базе из доверенной машины с production
   `DATABASE_URL`: `npm run db:migrate`. Затем запустите первый deploy.
5. После назначения домена обновите Clerk: добавьте домен в разрешённые домены
   приложения и выставьте адрес сайта как production URL. Проверьте вход, каталог,
   `/v1/models` и тестовый запрос через API.

Обязательные переменные Netlify:

- `DATABASE_URL` — отдельная production MariaDB; не используйте локальный
  адрес `localhost`.
- `CHEAPVIBE_API_KEY` — серверный ключ поставщика.
- `CLERK_SECRET_KEY` и `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` — ключи production
  экземпляра Clerk.
- `NEXT_PUBLIC_CLERK_SIGN_IN_URL=/auth/sign-in` и
  `NEXT_PUBLIC_CLERK_SIGN_UP_URL=/auth/sign-up`.

Для CryptoBot дополнительно задайте `CRYPTO_BOT_MODE` и соответствующий токен;
оставьте эти переменные пустыми, если пополнения не нужны. `DATABASE_ADMIN_URL`
используется только для первоначальной настройки базы и не требуется приложению.

Учитывайте лимит функций Netlify: синхронная обработка и потоковый ответ могут
работать не дольше 60 секунд. В SpiritLM таймаут генерации — 90 секунд, а
Next.js routes объявляют `maxDuration = 120`; генерация, которая длится дольше
лимита Netlify, может завершиться обрывом ответа. Для реального API трафика
выберите платформу с поддержкой нужной длительности или отдельно сократите
таймауты приложения до лимита хостинга.

Для CryptoBot webhook задайте URL `https://ваш-домен/api/payments/cryptobot/webhook`.
Netlify Scheduled Function `crypto-reconcile` запускает ту же сверку раз в минуту
по UTC после production-деплоя. Для ручного запуска локально используйте
`npm run payments:reconcile`.

## Vercel

Передать в Environment Variables серверные `DATABASE_URL`, `CHEAPVIBE_API_KEY`, `CLERK_SECRET_KEY` и публичные настройки Clerk/API. Применить миграции отдельно; при установке зависимостей Prisma Client генерируется через postinstall. Настроить доступ MariaDB с инфраструктуры Vercel и подходящие правила Clerk для домена.

Route Handler использует Node.js, предел длительности 120 секунд и таймаут поставщика 90 секунд. План Vercel должен поддерживать эту длительность. На экземпляр приложения создаётся пул максимум из трёх соединений; учитывать число экземпляров при настройке лимитов MariaDB. Публикация в рамках этой задачи не выполнялась.


## Банковские карты через ЮKassa (тестовый этап)

В окне пополнения представлены CryptoBot и банковская карта. Данные карты
пользователь вводит на странице ЮKassa; приложение их не получает и не хранит.
Перед созданием счёта сервер проверяет `/me` и наличие `bank_card` в списке
`payment_methods`. Если карты недоступны, запрос возвращает понятную ошибку
без создания записи платежа.

Для настройки интеграции задайте в `.env.local`
`YOOKASSA_MODE=test`, `YOOKASSA_SHOP_ID` тестового магазина и соответствующий
`YOOKASSA_SECRET_KEY_TEST` (ключ `test_…`). Параметры провайдеров независимы:
неработающий CryptoBot не препятствует оплате картой. Секреты остаются на сервере.

Примените миграции командой `npm run db:migrate`. Платежи ЮKassa хранятся
отдельно от счетов CryptoBot. Успешная тестовая оплата увеличивает только
`testBalance`; основной баланс и журнал реальных зачислений не изменяются.
`YOOKASSA_MODE=live`, пустой или неизвестный режим отключают оплату картой на этом этапе.
`YOOKASSA_SECRET_KEY` зарезервирован для следующего этапа: перед запуском
реальных оплат необходимо определить параметры чеков и правила зачисления.
Чеки, возвраты и автоматические списания сейчас не реализованы.

В тестовом магазине ЮKassa в разделе «Интеграция → HTTP-уведомления» задайте
`https://ваш-домен/api/payments/yookassa/webhook` и события `payment.succeeded`,
`payment.canceled`. Для локальной проверки нужен публичный HTTPS-туннель.
Webhook сверяет платёж через API магазина и не доверяет данным уведомления.
Возврат из ЮKassa открывает `/dashboard?payment_method=bank_card` с окном проверки.

Netlify запускает отдельную защищённую фоновую сверку ЮKassa раз в минуту.
На другом хостинге настройте ежеминутный запуск
`npm run payments:reconcile:yookassa`. Окно пополнения также проверяет статус
автоматически и по кнопке. После потери ответа создания повторяется исходный
запрос с сохранёнными телом и ключом идемпотентности в течение 23 часов;
затем выполняется поиск исходного платежа по metadata без нового списания.
Если статус установить не удалось, платёж остаётся на сверке, пользователь
получает предложение обратиться в поддержку. После ошибки автоматическая
проверка в окне останавливается до ручной повторной проверки. Кнопка отмены
доступна после получения ссылки на оплату. Сначала проверяется исходный
платёж, затем отправляется запрос отмены, если он в `waiting_for_capture`.
Для неоплаченного платежа (`pending`)
кнопка отмены скрывает ссылку на сайте; выбор сохраняется в `dismissedAt`.
Карта выбрана по умолчанию при каждом открытии окна. Через 10 минут после
создания ссылка на сайте закрывается автоматически и можно создать новый счёт.
Это локальный срок: API ЮKassa позволяет отменять только `waiting_for_capture`,
поэтому уже открытая страница провайдера может оставаться доступной дольше.
Фоновая сверка и webhook продолжают учитывать скрытые и просроченные счета:
поздняя успешная оплата зачисляется один раз. Для локальной отмены примените
миграцию `202610230001_dismiss_yookassa_payments`.

Проверки используют mock ЮKassa и не создают настоящих платежей.
Ручная проверка: выбрать банковскую карту, открыть страницу ЮKassa и оплатить
тестовой картой из документации провайдера. После возврата проверить тестовое
зачисление; повторный webhook или проверка не должны увеличить баланс снова.
Автоматические тесты проверяют создание карточного платежа, недоступность карт,
идемпотентность, восстановление после потери ответа и отмену с mock API.
Старые записи СБП восстанавливаются с исходным способом оплаты, описанием,
return URL и ключом идемпотентности; новые счета создаются только для карт.

## Подписки

В кабинете доступен раздел `/dashboard/subscription`: состояние пакета, расход и резерв кредитов, лимиты нагрузки, будущие оплаченные периоды и история покупок.

| Тариф | Цена за 30 дней | Кредиты | Запросов/мин | Параллельных генераций |
| --- | ---: | ---: | ---: | ---: |
| Nova | 390 ₽ | 645 | 10 | 2 |
| Vega | 990 ₽ | 1 800 | 30 | 5 |
| Sirius | 1 990 ₽ | 3 750 | 60 | 8 |

Один кредит оплачивает использование на 1 ₽ по обычному тарифу модели. Кредиты и денежный баланс хранятся отдельно. Nova исключает GPT 6 Astra и Claude Fable 5/5.1; эти модели доступны с API-баланса. Период длится ровно 30 суток в UTC. Остатки не переносятся. Следующая покупка добавляется после уже оплаченных периодов; текущий пакет не сбрасывается. Автопродления нет.

У каждого API-ключа есть `useSubscription` и `allowBalanceFallback`, по умолчанию оба выключены. Их можно передать при создании ключа и менять через `PATCH /api/dashboard/keys/[id]`. При включённой подписке запрос сначала полностью резервируется из пакета. Если подписка не действует, модель исключена или кредитов для резерва недостаточно, переход на API-баланс разрешается только при `allowBalanceFallback`. Резерв одного запроса не делится между источниками. Превышение лимита нагрузки не вызывает переход на баланс.

Лимиты подписки общие для всех ключей пользователя. Бесплатный доступ и запросы с API-баланса ограничены 20 запросами/мин и 1 параллельной генерацией. Окон на 5 часов и неделю нет. При финализации неиспользованный резерв возвращается в исходный период, даже если он уже закончился; неизвестный usage обрабатывается так же, как при оплате балансом. Подробное объяснение расхода пакета также доступно в документации кабинета.

`GET /api/dashboard/subscription` возвращает пакеты, остаток, резерв и историю. `POST /api/dashboard/subscription/checkout` принимает `planId`, `method` (`balance`, `card`, `cryptobot`) и UUID `requestId`. Сумму и объём пакета определяет сервер. Статус заказа доступен через `GET /api/dashboard/subscription/orders/[id]`; `DELETE` закрывает неоплаченный счёт. Все маршруты проверяют сессию и принадлежность данных.

Оплата с основного баланса атомарно списывает цену и выдаёт оплаченный период. Подтверждённый live-платёж CryptoBot выдаёт пакет напрямую, без пополнения денежного баланса. Webhook и существующие команды `payments:reconcile` / `payments:reconcile:yookassa` восстанавливают незавершённое исполнение. Назначение платежа определяется его связью с заказом подписки; старые платежи остаются пополнениями. Повторное подтверждение не выдаёт пакет дважды.

ЮKassa пока работает только в тестовом режиме. Тестовые покупки картой и CryptoBot создают отдельные тестовые периоды, не меняют основной или тестовый денежный баланс и не дают доступ к реальным генерациям. Боевой режим ЮKassa и автоматическое продление не входят в эту реализацию.
